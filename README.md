# Gate5 提出物

社内共用PCの貸出・返却アプリです。高優先度の例外系を中心に、二重貸出と複数テーブル更新の不整合を防ぎます。提出必須画像の撮影に必要な過去日チェックも実装しています。

## 1. 起動手順

### 環境構築と起動

- Python 3.9以上（標準ライブラリのSQLiteを使用）
- 外部パッケージのインストールやNode.jsは不要
- macOS / Linuxは `python3`、Windowsは `py` に読み替えて実行

```bash
git clone https://github.com/kurihara-vexum/NEXUS-Gate5.git
cd NEXUS-Gate5
python3 app.py --demo
```

[http://127.0.0.1:8000](http://127.0.0.1:8000) をブラウザで開きます。終了はターミナルで `Ctrl+C`。

初回起動で `data/gate5.db` を作成します。再起動しても貸出・返却データは残ります。データベースやCookieはGitへ登録しません。

ポートが使用中なら `python3 app.py --demo --port 8001` で起動し、末尾を `:8001` に変更します。撮影用データを最初から用意したい場合は、既存データを削除せず、未使用のDBファイル名を指定します。

```bash
python3 app.py --demo --db data/shoot-01.db
```

初期状態はPC-0001・0003・0004が貸出可能、PC-0002が佐藤花子に貸出中です。操作ユーザーは山田太郎。利用目的などを入力し、確認画面の「確定」で貸出します。「借りている端末」から返却できます。表示される社員はすべて架空のデモデータです。

`--demo` は撮影・検証用の「動作確認」画面を有効にします。通常画面だけで起動する場合は `python3 app.py`。このアプリは127.0.0.1に限定した課題用であり、実在の社員ログインや社内SSOは未実装です。本人照合はサーバーが割り当てるデモセッションを基準にしています。実運用向けの公開サーバーではありません。

### 検証

```bash
python3 -m unittest discover -s tests -v
```

18テストを実装。別接続からの同時申請、同じリクエストの再送、DBの一意制約、貸出・返却途中の失敗、実際のDBロックタイムアウト、社員状態の再検証、他人のID、確認内容の差し替え、CSRF、表示のエスケープ、4種類の提出画面へのHTTP応答を確認します。テストは一時DBで動くため、撮影用データには影響しません。

## 3. 実装した項目 / 実装しなかった項目

優先度は元の例外系洗い出し表に従います。高優先度の6項目を実装し、同じ仕組みで防止できる重複・再送や、撮影・安全な保存に必要な入力チェックを併せて実装しました。

| No | 項目 | 優先度 | 実装 | 理由 |
|---|---|---|---|---|
| 1 | 選択端末が既に貸出中 | 高 | 済（E-01） | 申請時に状態確認。確定時にもロック内で再確認し、二重貸出を防ぐ |
| 2 | 休職・退職社員の申請 | 高 | 済（E-02） | 申請時・確定時に社員がACTIVEか確認 |
| 3 | 貸出可能端末が0件 | 低 | 未 | 全件表示と各端末の状態チェックはあるが、E-03の専用表示は後回し |
| 4 | 貸出上限台数 | 中 | 未 | 上限値が未確定。データ整合性の対策を優先 |
| 5 | 同じ申請を2回行う | 中 | 済（E-05 / E-07） | 別の確認申請で同じ端末を重複確定するとE-05。同一確認の再送はE-07 |
| 6 | 2人が同じ端末を同時に選ぶ | 高 | 済（E-06） | BEGIN IMMEDIATEで直列化し状態再検証。未返却のdevice_idにも一意制約 |
| 7 | ブラウザバックからの再送信 | 中 | 済（E-07） | 確認トークンの消費状態をDBに保存。完了時は303でGETへ遷移 |
| 8 | 返却予定日が過去 | 中 | 済（E-08） | 提出必須の入力エラー画像のため実装。確定時も再検証 |
| 9 | 返却予定日が1か月超 | 中 | 未 | 高優先度と必須撮影条件を優先。1か月超の日付は現時点で許可される |
| 10 | 存在しない日付 | 中 | 済（E-10） | 不正な日付を保存しないための基本検証 |
| 11 | 返却予定日が当日 | 中 | 済（E-11） | 「明日以降」を満たす日付検証と共通化 |
| 12 | 返却予定日が空欄 | 中 | 済（E-12） | 保存に必要な最低限の検証 |
| 13 | 利用目的が空欄 | 中 | 済（E-13） | 空白をトリムして必須チェック |
| 14 | 利用目的が100文字超 | 中 | 済（E-14） | 定義した保存上限をサーバー・DBの双方で守る |

| 17 | 延滞ユーザーの新規貸出 | 中 | 未 | データ破壊防止と必須撮影条件を優先 |

| 19 | DB接続断・タイムアウト | 高 | 済（E-19） | SQLite操作エラー時にロールバック。実DBロックのタイムアウトと接続中断の模擬をテスト |
| 20 | 他人のIDを指定して実行 | 高 | 済（E-20） | デモセッションと送信IDを照合。確認トークン・貸出の所有者も検証 |

### 整合性を守る処理

貸出では、書き込みロックの取得 → 社員・確認トークン・入力・端末状態の再検証 → `lendings` 登録 → `devices.status='LENT'` → 確認トークンを消費 → COMMIT、を同じトランザクションで実行します。例外発生時はROLLBACKします。

返却も `lendings.returned_at` と `devices.status='AVAILABLE'` を一括で更新します。未返却の同じ端末を重複登録できない部分一意インデックスがあるため、画面のボタン無効化だけに依存しません。

`--demo` の「更新途中の失敗」は1つ目の更新後、意図的にDB制約違反を起こします。エラー表示だけを切り替えるモックではなく、実際のROLLBACKを通ります。「接続中断」はSQLite接続エラーの模擬で、物理的なネットワーク切断の再現ではありません。ロックによるタイムアウトは自動テストで実際に発生させています。

確定済みの申請を再送しても追加登録されません。COMMIT後にブラウザへの応答だけが途切れた場合も、再送による二重登録を防ぎ、「借りている端末」で結果を確認できます。

主要ファイル: `app.py`（HTTP・日本語画面・検証補助）、`domain.py`（入力・業務チェック・DB処理）、`static/`（表示）、`tests/`（自動テスト）。

## 4. モック画像一覧

**撮影は提出者が行います。以下は保存予定のファイル名で、まだ撮影済みとはしていません。** 保存先は `docs/mock/` です。

| ファイル名 | 撮影する状態 | 撮影手順 |
|---|---|---|
| `mock_01_正常_貸出完了.png` | 正常時の貸出完了 | 「動作確認」→「正常時の貸出完了」の「準備する」→「申請内容を確認する」→「確定」。端末番号・返却予定日・完了メッセージを撮影 |
| `mock_02_エラー_貸出中.png` | 既に貸出中の端末を選んだ状態 | 「動作確認」→「貸出中の端末」の「準備する」→「申請内容を確認する」。E-01と選択端末が分かる画面を撮影 |
| `mock_03_エラー_過去日.png` | 過去の返却予定日を入力した状態 | 「動作確認」→「過去の返却予定日」の「準備する」→「申請内容を確認する」。E-08と昨日の日付が分かる画面を撮影 |
| `mock_04_エラー_更新失敗.png` | 複数テーブル更新途中に失敗した状態 | 「動作確認」→「更新途中の失敗」の「準備する」→「申請内容を確認する」→「確定」。E-18が表示された画面を撮影 |

- エラー文言が読める大きさで撮影してください。画面全体が収まらない場合は、ウィンドウを広げるか表示倍率を調整します。
- 4枚目の撮影後、同じ確認画面で再度「確定」を押すと通常処理で成功します。障害は次の1回だけ有効です。
- 「動作確認」のデータ確認欄で、失敗前後の未返却件数・貸出中台数が同じで、不整合件数が0であることを確認できます。
- 正常貸出を繰り返して空き端末がなくなったら、「借りている端末」から返却できます。
- 同時実行を手動確認する場合は、別ブラウザまたは独立したプライベートウィンドウを使います。同一ブラウザ内のタブは同じセッションです。別々の社員に切り替え、同じ端末の確認画面を両方で開いてから確定すると、先行だけ成功し後続はE-06になります。
